# План реализации по этапам

Основа — раздел 11 ТЗ (`tz-tenderhack.md`), развёрнутый до конкретных задач по трекам. Общее окно — 30 часов. Три параллельных трека: **.NET** (домен/API/реальное время), **Python** (`ml` + `ingest`), **Frontend** (React). Трек .NET уже имеет каркас решения — см. `TenderHack.sln`.

Правило на все этапы: контракты `api` ↔ `ml` (раздел 5 ТЗ) фиксируются в первый час и не меняются без синхронизации — только так треки работают параллельно, а не последовательно.

---

## Этап 0 — Разбор данных и контракты (0–2 ч)

**Все вместе:**
- Скачать и просмотреть материалы (регламент, методички — раздел 2.6 ТЗ), выписать 15–20 типовых вопросов для будущего ЧАВО-кэша (раздел 8.1).
- Зафиксировать контракты `POST /triage`, `POST /answer`, `POST /search`, `POST /analytics/feedback` — они уже отражены в `TenderHack.Application.Abstractions.IMlService` и DTO в `MlModels.cs`. Если меняете форму ответа `ml`, правьте `MlServiceClient` и DTO синхронно.

**.NET (сделано в этой сессии, проверить и продолжить):**
- Решение `TenderHack.sln` с проектами `Domain / Application / Infrastructure / Web / UnitTests`, слои и правило зависимостей — раздел 9.1.
- Пустой `docker-compose.yml` в корне: `db` (pgvector) + `api` уже поднимаются; `ml`, `ingest`, `web` — закомментированные заглушки, раскомментировать по готовности.
- `MlServiceClient` уже реализован как HTTP-адаптер над контрактами из раздела 5, с деградацией к `no_answer` при любой ошибке (раздел 10) — командам Python достаточно поднять `ml` на `:8000` с этими путями, и интеграция заработает без правок .NET.

**Python:**
- Поднять пустой FastAPI на `:8000` с четырьмя роутами, отдающими правдоподобные заглушки JSON (эхо, случайная уверенность). Это разблокирует .NET и фронтенд немедленно.
- Отдать OpenAPI-схему (штатно из FastAPI) — пригодится для сверки контрактов, даже если C#-клиент писан руками (см. ниже).

**Frontend:**
- Инициализировать `web/` (React + Vite + TS), пустой чат-экран, заготовка `bpmn-js`.

> Примечание по разделу 5 ТЗ: там предполагается генерация C#-клиента через NSwag. В этом каркасе `IMlService`/`MlServiceClient` написаны вручную (см. `src/TenderHack.Infrastructure/Ml/MlServiceClient.cs`) — это осознанное упрощение для скорости старта: контракт из четырёх эндпоинтов проще поддерживать руками, чем чинить генератор под дедлайн. При желании можно подключить NSwag позже, заменив тело `MlServiceClient` на сгенерированный клиент — интерфейс `IMlService` (Application-слой) при этом не меняется, это и есть его роль как границы.

## Этап 1 — Сквозной путь на моках (2–8 ч)

**.NET (каркас уже готов, задачи — довести до работающего сквозного сценария):**
1. Поднять `db` в Docker, накатить первую EF-миграцию (`dotnet ef migrations add InitialCreate --project src/TenderHack.Infrastructure --startup-project src/TenderHack.Web`), проверить, что `AppDbContext` создаёт только `tickets/messages/message_analysis/feedback/specialists` — `kb_*` таблицы не должны появиться (раздел 6.1).
2. Прогнать `ProcessUserMessageHandlerTests` (уже есть, 3 сценария — мат / низкая уверенность / нормальный ответ) — они зелёные на моках уже сейчас, это и есть доказательство развязки слоёв.
3. Проверить сквозной путь через `ChatHub`/`OperatorHub` вручную (например, через простой HTML/wscat) — сообщение пользователя доходит до `ProcessUserMessageHandler`, ответ/эскалация уходят обратно через `SignalRChatNotifier`.
4. Реализовать `GetOperatorQueueHandler`/кабинет оператора минимально — эндпоинты уже есть в `TicketEndpoints`, не хватает только фронтенда.

**Python:**
- `ingest`: скачивание регламента и методичек, чанкинг по заголовкам (раздел 4.1), запись в `kb_chunks`/`kb_documents` (SQL-скрипт, не EF — раздел 6.1).
- Гибридный поиск: BM25 (`to_tsvector('russian', ...)`) + pgvector, RRF-слияние одним CTE.
- Эмбеддинги `intfloat/multilingual-e5-small`, SymSpell поверх словаря из базы знаний.

**Frontend:**
- Подключение к `ChatHub`, простой рендер сообщений пользователь/бот/оператор со статусами.

## Этап 3 — Аналитика, генерация, BPMN (16–24 ч)

**Python:**
- `/answer`: llama.cpp, модель 1.5–3B Q4_K_M, строгий RAG-промпт, гибридная стратегия по уверенности (раздел 4.2). Фолбэк — экстрактивный ответ, если генерация нестабильна.
- `/analytics/feedback`: тональность → эмбеддинги негатива → кластеризация (k-means/HDBSCAN).
- Кэш типовых вопросов (раздел 8.1) — точное совпадение + похожесть эмбеддингов ≥0.95, прогрев из ЧАВО.

**.NET:**
- `AnalyticsRefreshService` уже реализован (раз в минуту, SQL-метрики + вызов `ml.ClusterFeedbackAsync` для негатива, кэш в `IAnalyticsCache`) — подключить к реальным данным, когда появятся тикеты с отзывами.
- `GetAnalyticsHandler`/`AnalyticsEndpoints` отдают снапшот из кэша, ничего не ждут от Python (раздел 7.3) — уже так и работает.

**Frontend:**
- Дашборд аналитики (Recharts) — это 20 баллов, которые часто недобирают (акцент из раздела 11 ТЗ).
- Встраивание BPMN-схемы через `bpmn-js` прямо в интерфейс (раздел 4.5).

## Этап 4 — Заморозка и репетиция (24–30 ч)

- Прогон на реальных кейсах организаторов, подбор порога `MinConfidence` через `/api/admin/threshold`.
- Проверка деградации: погасить контейнер `ml` и убедиться, что `api` не падает и корректно эскалирует все обращения (`MlServiceClient` уже это гарантирует — раздел 10, DoD п.4).
- Собрать демо-сценарии: вопрос → ответ из базы; вопрос вне базы → эскалация; мат → автозакрытие; отзыв → аналитика (DoD п.5). Эти четыре ветки не режутся никогда.
- Дописать README (диаграмма слоёв, правило зависимостей, команда запуска, обоснование моделей — DoD п.7).

### Порядок сокращения при нехватке времени (без изменений от раздела 11 ТЗ)

1. Локальная LLM → экстрактивные ответы с подсветкой фрагмента.
2. Кластеризация проблем → заранее заданные категории с частотами.
3. Личный кабинет оператора → один общий экран очереди.

Не режется никогда: сообщение об отсутствии ответа в базе знаний и автозакрытие по мату.

## Состояние каркаса .NET на конец этапа 0

Уже реализовано и собирается (`dotnet build` — 0 предупреждений, 0 ошибок; `dotnet test` — 10/10 зелёных):

- **Domain**: `Ticket` (агрегат со всеми переходами и инвариантами), `Message`, `MessageAnalysis` (owned), `Feedback`, `Specialist`, перечисления, `TicketTransitionException`, `SourceRef`.
- **Application**: все девять обработчиков из раздела 9.3, порты (`ITicketRepository`, `IUnitOfWork`, `IMlService`, `IChatNotifier`, `IOperatorNotifier`, `IAnalyticsCache`, `IDateTimeProvider`, `IThresholdProvider`), `Result<T>`, DI-регистрация.
- **Infrastructure**: `AppDbContext` + `IEntityTypeConfiguration<T>` по файлу на сущность, `TicketRepository`, `UnitOfWork`, `MlServiceClient` (с Polly-ретраями и безопасной деградацией), `AnalyticsRefreshService`, `SystemDateTimeProvider`, `OptionsThresholdProvider`, `MemoryAnalyticsCache`, DI-регистрация с HTTP-клиентом на `ml`.
- **Web**: Minimal API по `IEndpointGroup` (`Chat`, `Ticket`, `Feedback`, `Analytics`, `Admin`), `ChatHub`/`OperatorHub` + SignalR-адаптеры нотификаторов, `ExceptionHandlingMiddleware`, Serilog, Swagger, CORS, `/health`, composition root в `Program.cs`.
- **Tests**: `TicketTests` (7 тестов на переходы/инварианты), `ProcessUserMessageHandlerTests` (3 сценария пайплайна на фейках).
- **Инфраструктура репозитория**: `Directory.Build.props`, `docker-compose.yml` (db + api сейчас, ml/ingest/web — заглушки), multi-stage `Dockerfile` для `api`.

Не сделано намеренно (относится к Python/Frontend трекам или следующим этапам): EF-миграции ещё не сгенерированы (нет смысла до финализации схемы), `kb_*` SQL-скрипт, сама модель в `ml`, фронтенд, BPMN-схема.
