Architecture map

The same system, one level up from Docker: who owns which decision, and — deliberately drawn as three separate stores — which of them owns the State, the plain relational Knowledge metadata, and the Vector & Lexical Index.

≠ Not what the rule actually says: the project never isolates Python to "only the vector DB." The rule is no cross-runtime table access — knowledge never touches api's tables and vice versa. knowledge still owns a completely ordinary relational store (Knowledge Store) in addition to the vector/lexical index — both live under its own knowledge_rw role, both inside the same physical PostgreSQL 16. Drawn below as separate abstractions because that's the useful mental model, not because they're separate servers.

Python-owned, relational (knowledge_rw)
Python-owned, vector/lexical (knowledge_rw)

What this actually enforces

  1. No cross-runtime table access — not "no relational access for Python." knowledge freely owns its own relational tables (Knowledge Store); it just never sees api's State Store, and api never sees either of Python's stores.
  2. One direction only. api → knowledge, always, over contract v0. knowledge never calls back and never reads api's tables.
  3. Vector and relational are one role, two shapes. Both Python stores share knowledge_rw — the split into two boxes is for legibility, not a second database service.
  4. Stage, specialist and outcome are adapter facts only. They enter through IngestHandoffStatus (poll or signed webhook) and nowhere else; a null stays null, the UI never shows a placeholder specialist. RESOLVED is set only by the user's complete or by a terminal adapter fact.
  5. Notifications are api-owned facts, delivered locally. Persisted inbox + owner-level SSE + browser Web Notifications API. No Web Push, email or SMS in P0 — they need external services and would break the offline demo (ADR-0002).

Шпаргалка: кто есть кто и кто кому звонит

Без формальностей — просто «что это» и «чем реально общаются» для каждой стрелки на схеме выше.

Browser клиент Обычный браузер пользователя. Ничего не знает про knowledge — только про web и api.
web frontend React SPA. Отдаёт статику браузеру и сама же ходит в api из JS (fetch/EventSource) — на схеме это одна стрелка «HTTP/SSE», не через web-контейнер.
api .NET · support core Единственная точка входа для браузера. Держит состояние кейса, считает Decision (вкл. MODERATION_WARNING), завершает обращение, пишет уведомления, дергает knowledge по контракту v0. Принимает опциональный подписанный webhook от поддержки.
api-worker .NET · фоновый процесс Тот же код что и api, но без HTTP-входа. Разгребает outbox: отправляет handoff, опрашивает статус принятых передач (handoff-status-sync), пушит turns / feedback / completions в knowledge.
knowledge Python · FastAPI Отвечает на синхронные вызовы api по v0: понять запрос, найти фрагменты, оценить достаточность, сгенерировать черновик, проверить его. Никогда не решает, никогда не зовёт api в ответ.
knowledge-worker Python · фоновый процесс Тот же код, без HTTP. Парсит документы, считает embeddings, гоняет quality audit по уже накопленным данным.
inference (vLLM) модельный runtime Просто сервер с моделями (embedder/reranker/generator). Вызывается только из Python-кода, у api к нему нет доступа вообще.
State Store таблицы Postgres Обычные таблицы: cases, turns, handoffs, handoff_status_updates, outbox, feedback, notifications. Читает/пишет только .NET-код через EF Core.
Knowledge Store таблицы Postgres Тоже обычные таблицы (kb_documents, quality_cases и т.п.), просто принадлежат Python-стороне. Обычный SQL, никакой магии.
Vector & Lexical Index расширения Postgres pgvector (похожесть по смыслу) + pg_trgm/FTS (похожесть по буквам). Физически те же таблицы Postgres, просто отдельный тип запроса.
Portal support system внешняя система (демо) На хакатоне это demo-адаптер: принимает заявку и по запросу отдаёт сценарий статусов («в очереди → назначен Демо-специалист → в работе → решено»), каждый шаг помечен SIMULATED. Настоящей интеграции нет; реальный адаптер встанет на тот же контракт.

Browser → web HTTP GET (обычная раздача файлов) Браузер скачивает HTML/JS/CSS собранного React-приложения.
Browser → api HTTP (REST) + два SSE-потока:
/cases/{id}/events/stream · /notifications/stream		 Обычные запросы (сообщение, «Обратиться к оператору», «Завершить обращение», feedback) плюс живой поток событий чата (стадии, ответ, предупреждение модерации, статус передачи) и отдельный owner-level поток уведомлений — он работает, даже если открыт другой чат; при скрытой вкладке браузер показывает системное уведомление (Web Notifications API, без внешних push-серверов). Доступ по анонимной owner-cookie.
api → knowledge HTTP POST, contract v0
/v0/understand, /v0/retrieve, /v0/answerability, /v0/draft, /v0/verify, /v0/moderation/context		 Синхронные вызовы внутри одного хода диалога. Каждый — отдельный HTTP-запрос с заголовками X-Trace-Id/X-Case-Id/X-Turn-Id. Ответ — факты и оценки, не решение.
api-worker → knowledge HTTP POST /v0/quality/turns, /v0/quality/feedback, /v0/quality/completions Асинхронный «пуш» фактов: ход, feedback (четыре сигнала: специалист, качество информации, «решено?», комментарий) и завершение обращения с исходом — через outbox, at-least-once, идемпотентно по turn_id+revision / feedback_id / case_id.
knowledge / knowledge-worker → inference HTTP (OpenAI-совместимый API vLLM) через узкие адаптеры Embedder / Reranker / Generator / Verifier «Посчитай embedding», «оцени релевантность пары», «сгенерируй structured draft», «проверь claim по evidence». Никакого произвольного tool-use, только эти 4 операции.
api → State Store SQL через EF Core / Npgsql, роль api_rw Обычные INSERT/UPDATE/SELECT в свои таблицы на каждый HTTP-запрос: сохранить сообщение, записать стадию хода, обновить состояние.
api-worker → State Store SQL через EF Core, роль api_rw SELECT ... FOR UPDATE SKIP LOCKED по таблицам outbox/api_jobs — забрать очередную задачу, пометить как отправленную/проваленную.
knowledge / knowledge-worker → Knowledge Store SQL через SQLAlchemy2/asyncpg, роль knowledge_rw Обычный SQL по своим таблицам: сохранить распарсенный документ, записать сохранённый quality-кейс, обновить issue-group.
knowledge → Vector & Lexical Index SQL: оператор <=> (pgvector cosine), %/similarity() (pg_trgm), to_tsquery (FTS) Тот же SQL-коннект что и выше, просто другой тип запроса — «найди похожие по смыслу/по буквам фрагменты», результаты которых потом соединяются (RRF) и передаются в reranker.
api-worker → Portal support system интерфейс IHandoffAdapter.SubmitAsync(...) (демо-реализация — эмулирует ответ по конфигу: success/timeout/failure) «Отправить заявку человеку». На хакатоне настоящего HTTP наружу нет — адаптер выбирается конфигом, а не запросом, и явно помечен как demo/simulated в UI.
Portal support system → api-worker интерфейс IHandoffAdapter.GetStatusAsync(...), job handoff-status-sync (poll с backoff 15 с → 5 мин) «Что там с моей заявкой?» — worker сам опрашивает адаптер по принятым передачам и получает HandoffStatusSnapshot: этап, специалист, терминальный исход. Идемпотентно по handoff_id + external_revision. Терминальный статус завершает обращение (CLOSED_SUPPORT) и порождает уведомление. Demo-адаптер отдаёт заранее заданный сценарий.
Portal support system → api (опционально) HTTP POST /api/v0/integrations/support/status, HMAC-подпись + timestamp; выключен, пока нет реального адаптера Тот же HandoffStatusSnapshot, но push'ем от реальной системы. Попадает в тот же use-case IngestHandoffStatus, что и polling, — Domain не различает канал. Demo этот путь не использует.
