# ADR-0002 — Inbound handoff status sync and in-app notifications

- **Статус:** accepted (2026-09-12)
- **Дополняет:** ADR-0001 (граница `api` / `knowledge`), `contracts/support-adapter-v0.md`, `contracts/web-api-v0.md`
- **Затрагивает:** `architecture.md §3, §5.6, §5.8–5.9, §6–8, §12–13, §15, §17`, `product-spec.md §3, §16–18`, `quality.md`, `execution-plan.md`

## 1. Контекст

Продуктовые требования (чат-first UX, 2026-09-12):

- после передачи в поддержку — виджет со статусом, **каким специалистом** занято обращение и **на каком этапе**;
- **уведомление о завершении** обращения;
- после завершения — архив и интерактивный feedback.

Архитектура до этого ADR умела только **исходящий** handoff: `IHandoffAdapter.SubmitAsync` + синхронный ack. Ни этап, ни специалист, ни терминальный статус не могли попасть в `api` иначе как выдумкой, что прямо запрещено (`AGENTS.md §3`: не изобретать данные интеграций). Уведомления существовали только как SSE открытого чата: закрытая вкладка = ничего.

Ограничения, которые нельзя нарушить:

- офлайн-демо без внешнего интернета (`quality.md §11 #12`);
- никаких внешних API в штатном контуре (`hackathon-requirements.md §3`);
- реальный API Портала поддержки неизвестен (`open-decisions.md OD-003`);
- никаких новых сервисов/очередей без измеренной причины (`stack.md §15`).

## 2. Решение

### 2.1. Inbound handoff status — два канала, один write path

| Канал | Кто инициирует | Когда |
|---|---|---|
| **Polling** — `IHandoffAdapter.GetStatusAsync`, job `handoff-status-sync` в `api-worker` | `api` | P0, обязательно; работает с demo-адаптером и с любой реальной системой, у которой есть read-endpoint |
| **Webhook** — `POST /api/v0/integrations/support/status`, HMAC-подпись, выключен по умолчанию | внешняя система | только для реального адаптера, который умеет push |

Оба канала выдают один и тот же `HandoffStatusSnapshot` и входят в один use-case `IngestHandoffStatus`, идемпотентный по `(handoff_id, external_revision)`. Domain не знает, откуда пришёл факт.

Этап и специалист — **nullable факты адаптера**, не Domain-enum. Терминальный статус адаптера — один из трёх легитимных путей завершения обращения (`architecture.md §5.8`), наряду с явным `complete` пользователя и модерационным закрытием.

Demo-адаптер получает детерминированный `staged`-сценарий (в очереди → назначен «Демо-специалист» → в работе → решено), помеченный `SIMULATED` на каждом шаге, чтобы UI-виджет и E2E были воспроизводимы без реальной поддержки.

### 2.2. Уведомления — api-owned факт, три уровня доставки

`notifications` — таблица `api`, строка пишется в той же транзакции, что и порождающее `case_event`. Scope — `owner_id` анонимной браузерной сессии (cookie, `web-api-v0.md §13`).

1. persisted inbox + badge (`GET /api/v0/notifications`) — переживает закрытый браузер;
2. owner-level SSE (`/api/v0/notifications/stream`) — toast в открытой вкладке; при скрытой вкладке браузер показывает системное уведомление через Web Notifications API — это локальный браузерный API, внешних серверов не требует;
3. Web Push / email / SMS — **не делаем** (§4).

## 3. Что мы принимаем как цену

| Минус | Смягчение |
|---|---|
| Polling создаёт фоновую нагрузку на адаптер | backoff 15 s → 5 min, TTL 7 дней, только non-terminal accepted handoffs; при реальном webhook polling можно отключить конфигом |
| Владелец без аккаунта: очистка cookie = потеря доступа к прошлым обращениям | приемлемо для хакатона, явно сказано в UI; аккаунты — post-hackathon |
| Web Notifications требует разрешения пользователя и открытой (пусть фоновой) вкладки | честно описано в UX; полностью закрытый браузер покрыт inbox'ом при возвращении |
| Webhook — публичная точка входа | HMAC + timestamp ±5 min + replay-защита по `external_revision`; не регистрируется без `Support:Webhook:Enabled` |
| +2 таблицы, +1 job, +4 публичных эндпоинта | все в `api`, без новых runtime/сервисов |

## 4. Отклонённые альтернативы

- **Только webhook.** Нечего демонстрировать без реальной системы, а её API неизвестен (OD-003). Polling работает с demo-адаптером сегодня.
- **Выдумывать этап/специалиста в UI по очереди/линии.** Прямо запрещено; на защите это ложь, а не демо.
- **Web Push (VAPID).** Зависит от внешних push-сервисов браузеров (Google/Mozilla/Apple) → ломает офлайн-демо и требование «без внешних API». Возможный P1, если организаторы разрешат внешний канал доставки.
- **Email/SMS.** Продукт не собирает контакты; нужен внешний провайдер или новый сервис в Compose (MailHog/Mailpit только для демо — не решает продуктовую задачу).
- **Отдельный notification-сервис / Redis pub-sub.** SSE из `api` + таблица покрывают масштаб хакатона; `stack.md §15` запрещает сервис без измеренной причины.
- **Новое значение `HandoffStatus` (`RESOLVED`).** Смешивает transport-статус передачи с исходом обращения; исход живёт в `ResolutionStatus`, закрытие — в `ConversationStatus = CLOSED_SUPPORT`.

## 5. Условия пересмотра

- появился реальный API Портала с push-моделью и без read-endpoint → polling выключается конфигом, webhook становится основным (без изменения Domain);
- организаторы явно разрешили внешний push/email → отдельный ADR для Web Push как P1;
- измеренная нагрузка polling'а на реальный адаптер > согласованного лимита → пересмотр backoff/TTL, не архитектуры.
